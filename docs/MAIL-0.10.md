# Shared reception, notices and polling

Administration activates one existing SMTP/IMAP account at reception.php. Activation records UIDVALIDITY/UIDNEXT and skips pre-existing mail. Employees with external-send permission can select the shared account in the internal composer. Replies from an assigned reception message default to that public account. Credentials remain server-side. Virtual internal addresses are not provider aliases: direct delivery to those addresses still requires provider aliases or catch-all.

Outgoing shared messages receive an opaque HMAC-signed marker in an HTML comment, a hidden sent-by label and X-TNL-Route, plus stored Message-ID mappings. Incoming assignment prioritizes an explicit active internal recipient, then RFC references, then the verified marker. Reference/marker routing also requires the incoming sender to be a peer of that conversation. One sender may have separate conversations with different employees. No assignment is inferred solely from a sender's previous contact.

A first unassigned contact receives one automatic prompt with up to 40 active names, job titles and internal addresses. A unique exact normalized name/address/department choice assigns that pending thread; ambiguity stays in the admin queue. Auto-Submitted, list/bulk/junk flags, recognized spam, null return paths and no-reply senders suppress automatic responses. Sending is reserved before SMTP and never automatically retried on uncertainty. Prompt rate is capped at 10 new contacts per hour. Shared reception is deduplicated by mailbox/UIDVALIDITY/UID and Message-ID; workers serialize via a private lock. Oversized or structurally invalid messages are recorded for manual provider review and are never deleted from IMAP.

Reception assigned mail is a separate account-scoped inbox backed by SQLite with sanitized HTML, inline images and conversation reading. Only the assignee (or admin) can read its messages; admin can reassign a conversation.

Notifications query internal unread/shared assigned mail and notices every 60 seconds while the app is open, and check the selected/default external account and shared reception every 300 seconds. Browser timers may be throttled by background/power-saving policies. Desktop notifications require the user's explicit browser permission button. The CLI entry is app/Mail/ReceptionWorker.php: configure a hosting cron to run it each minute for continuous reception when all app tabs are closed; it enforces the 300-second poll cadence. No hosting cron was configured by this release.

Notices: admin grants/revokes publishing per user; everyone authenticated can comment with Jodit rich HTML. Author/global pins and individual reader pins are separate. Tags: important red, security slow red/blue animation, informational green, mandatory yellow, optional blue. Reduced-motion preference disables the animation. Content uses the mail sanitizer; removing a notice is a soft delete.

Tests cover routing isolation, marker tampering, client separation, direct recipient precedence, selection of an assignee from an auto-prompt reply, replay prevention, loop suppression, permissions, sanitized notices, personal/global pins and notification read cursors. Browser fixtures use fictitious accounts and SMTP stubs; real deployment diagnostic sends one fixed loopback from claudetest@cache.lat to itself and verifies imported assignment separately.

Automatic notification requests do not refresh the device PIN inactivity timestamp. New HTML-only selection replies are normalized into lines before directory matching. Hosting cron remains a separate administrator setup step.
